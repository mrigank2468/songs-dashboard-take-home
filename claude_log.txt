  2. Precedence: part1 wins on conflicts. Within one file, the first row for an

  3. Conflicts: When both sources have a valid value and they differ, the report
     records the field, the chosen and other values, and both original raw
     values. Values are compared after cleaning, so "0.5" and 0.5 don't count as

     source has a valid one, I fill it and record that in
     filled_from_other_source. This is how the four overlapping songs get their
     valence.
  5. Nulls: A missing key, null, "" or whitespace-only string, and "N/A", "na",

  6. Numeric strings: Valid ones convert to numbers and are logged as
     type_coercion.

  Behavior

  GET /songs?sort_by=tempo&order=desc&page=2&size=10

  Endpoint contracts

  - GET /songs: takes page, size, sort_by, order and the new title (all examples
    are in the README).
    - It filters by title, sorts the whole result, then paginates. total and
      total_pages describe the filtered set.
    - A blank title means no filter. A search with no matches returns {"songs": 
      [], "page": 1, "size": 10, "total": 0, "total_pages": 0}.
    - Each song now has a rating field, null until rated. sort_by=rating works,
      with unrated songs last.
  - PUT /songs/{song_id}/rating: sends {"rating": 5} and returns {"song_id": 
    "7fBv7C…", "rating": 5}.
    - Only an integer from 1 to 5 is accepted. Strings, floats, booleans, null,
      a missing value and extra keys all return 422.
    - An unknown id returns 404 {"detail": "Song not found: nope"}, checked
      before the body.
  - GET /songs/{song_id}/rating: returns the rating, or null if unrated.

  How ratings are persisted

  Ratings go in backend/data/ratings.db, a SQLite file written through Python's
  built-in sqlite3, separate from the song data. Each rating is one atomic
  upsert on one row, so rating one song can't drop another's rating. Concurrent
  threads and processes are safe. The file is gitignored.
